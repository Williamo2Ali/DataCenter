# خطة المستودعات المشفرة (EncryptedRepos)

> الحالة: قرار مالك التطبيق — كل مستودع = ملف مشفر واحد ("مستودع" اسم أليف للحاوية). ما عداها مرفوض والتطبيق بدونه إلى القمامة.
> القاعدة الذهبية: لا بايت نصي مفهوم خارج المظروف المشفر — يُتحقق منها آلياً لا بالثقة.

## 1. التشخيص الصادق (لماذا الهجرة)

* الرؤية الأصلية: حاوية مشفرة كـ rar/zip — كل شيء مشفر بما فيه البيانات الوصفية.
* المنفَّذ: مجلد نصي (`data.db` + `repo.json` + `files/`) + بوابة كلمة مرور، والواجهة تدّعي "مشفر بكلمة مرور" كذباً.
* النتيجة: تنظيم بلا حماية قرص. التشفير الحقيقي الوحيد يعيش في نظام الحاويات القديم (`.vault`).
* القرار: العودة للأصل — المستودع ملف مشفر واحد، لا مجلد.

## 2. الصيغة المستهدفة

* ملف واحد per مستودع بامتداد مخصص، البنية: `MAGIC | version | salt | iv | AES-256-GCM(payload)` — إعادة استخدام مظروف `vault.rs` (`encrypt_envelope`) المجرّب، ببصمة سحرية جديدة خاصة بالمستودعات.
* الحمولة حاوية منظمة (zip داخلي كما في `.dcbackup`): القاعدة + البيانات الوصفية + الملفات — كلها داخل التشفير.
* كلمة المرور: كلمة المستودع نفسها (مشتق PBKDF2 بـ 120k كالحالي) — لا كلمات جديدة على المستخدم.
* كشف القفل بلا كلمة مرور: البصمة السحرية فقط (ملف حاوية أم لا)، لا أعلام نصية ولا أسماء خارجية.

## 3. القاعدة الحية (قرار تقني ملزم)

* رفض نهائي لفك الحاوية لملف مؤقت عند الفتح (نافذة مكشوفة + نسخ مئات MB على الهواتف).
* المعتمد: **SQLCipher** (تشفير على مستوى صفحة SQLite) للقاعدة + تشفير تدفقي (مقاطع، كملحق `file-copy`) لملفات `files/`.
* أي بديل أرخص يُرفض في المراجعة — يُكتب سبب الرفض هنا لا في الكود.

## 4. البيانات الوصفية والأسماء (قرار مالك — معلّق)

* إن كانت الأسماء داخل التشفير: قائمة الرئيسية للمقفلة تعرض "مقفل — يلزم كلمة المرور" بلا اسم حتى تُفتح.
* وإن قُبِلت ترويسة خارجية بالاسم فقط: تُعامل كتلميح غير موثوق (أي اختلاف مع الداخل = تعارض ظاهر).
* الافتراضي المقترح: لا أسماء خارج التشفير إطلاقاً.

## 5. التقسيم الإجباري (لا ملف واحد أبداً)

* طبقة التخزين الجديدة تولد مقسمة: `repos/` مجلداً — `mod.rs` (فتح/إنشاء/حذف + فهرس) + `peoples.rs` + `passports.rs` + `documents.rs` + `accounts.rs` + `contacts.rs` + `custom_tabs.rs` + `columns.rs` + `common.rs`.
* العمليات العابرة للجداول (حذف شخص = 6 جداول في معاملة) تبقى معاً بملكية واحدة معلنة.
* لا يُعاد تنظيم الكود الميت (`repos.rs` الحالي) — التقسيم يحدث أثناء الهجرة فقط.

## 6. الأنظمة القائمة فوق التخزين

* **الفهرس العام** (`people_index.json`): يبقى — ينسخ الأسماء لحظة الكتابة والمستودع مفتوح، فيُبحث في المقفلة دون فتحها.
* **المشاركة:** الحاوية المشفرة ملف واحد أصلاً — النسخ على فلاشة/USB هو التصدير، والاستيراد فك وفحص. بلا `zip` إضافي.
* **Drive:** مطوية نهائياً (بلا OAuth) — لا تُبنى مزامنة فوق الحاويات.
* **الواجهات:** الشاشات والبحث والفهرس تُعاد توصيلها فوق الملف الواحد؛ سلوك المستخدم لا يتغير.

## 7. البيانات الحالية

* كلها وهمية بقرار المالك — بلا ترحيل. حاويات جديدة نظيفة، والقديم يُحذف.

## 8. بوابات القبول (تُكتب قبل الكود، وتفشل أولاً)

1. فحص بايتات القرص الخام لأي مستودع مقفل: أي نص مفهوم (اسم/هاتف/بايتات SQLite) = فشل.
2. كلمة خاطئة تُرفض، وعبث بايت واحد يُكتشَف (GCM) ولا يُفتح.
3. فتح بكلمة صحيحة يعرض كل البيانات سليمة + كتابة وقراءة دورة كاملة.
4. حذف/فقدان كلمة المرور = فقدان البيانات نهائياً (يُوثَّق للمستخدم صراحة — بلا باب خلفي).
5. فتح نفس الحاوية على جهازين (نسخة منقولة) يعمل بكلمة واحدة.
6. مراجعة بشرية: فتح ملف الحاوية بمحرر hex من المالك نفسه.

## 9. الشرائح (عرض حي بعد كل شريحة، لا تسليم ضخم)

1. حاوية فارغة: إنشاء/فتح/إغلاق بكلمة مرور + بوابة القبول 1 و2.
2. البيانات الوصفية والأشخاص داخل الحاوية + الفهرس العام.
3. الجداول الأربعة (SQLCipher) + الحسابات وجهات الاتصال.
4. الملفات (تشفير تدفقي) + المشاركة كملف واحد.
5. إسقاط نظام المجلدات النصية + إعادة التسمية الصادقة (مقفل/مفتوح بدل مشفر).

## 10. مرفوض صراحةً

* كتابة تنفيذية بالذكاء الاصطناعي (مواصفات ومراجعة فقط)، فك المؤقت، أعلام نصية خارج المظروف، `SQLite` عادية بلا تشفير، ترحيل البيانات الوهمية، مزامنة تلقائية، Drive/OAuth بأي شكل.
